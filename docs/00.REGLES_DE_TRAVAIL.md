# Règles de travail du projet

> Ce document consigne les conventions appliquées à chaque contribution. Il existe pour
> deux raisons : qu'un nouvel arrivant n'ait pas à les deviner, et qu'aucune ne repose sur
> la seule mémoire de ceux qui les ont posées.
>
> Les règles marquées **vérifiée** sont contrôlées par la suite de tests. Les autres
> relèvent de la discipline, et sont donc les plus fragiles.

---

## 1. Langue du code · *vérifiée*

**Commentaires et docstrings en anglais**, dans tout le code source et dans les cellules de
code des carnets.

**Contenu affiché en français** : cellules markdown, titres et libellés de figures, noms de
colonnes des tableaux produits, messages imprimés et messages d'exception.

| Élément | Langue | Motif |
|---|---|---|
| Commentaires `#` | Anglais | Convention usuelle, lisible par tout relecteur technique |
| Docstrings | Anglais | Elles documentent l'implémentation, pas le livrable |
| Noms de fonctions et de variables | Français | Héritage assumé ; renommer l'API publique est une opération à mener hors période de remise |
| Markdown des carnets | Français | Le livrable est lu par un jury francophone |
| Titres et libellés de figures | Français | Idem |
| Messages imprimés et d'exception | Français | Ils apparaissent dans les sorties remises |

Le résultat est un hybride assumé : identifiants français, commentaires anglais. C'est un
compromis fréquent en contexte professionnel francophone.

**Contrôle :** `tests/test_conventions.py` signale tout commentaire ou docstring contenant
un caractère accentué — un indice fiable et peu coûteux de prose française. Le même fichier
vérifie l'inverse sur les tables affichées : leur contenu doit rester accentué.

## 2. Synchronisation avant toute mise à jour · *procédure*

Avant de commencer quoi que ce soit :

```bash
git fetch origin
git log --oneline -3 origin/develop
git rev-list --left-right --count origin/develop...HEAD
```

**Pourquoi.** L'historique distant a déjà été réécrit une fois. Travailler sur une base
périmée produit des patchs qui ne s'appliquent plus et, pire, des corrections qui écrasent
celles de quelqu'un d'autre.

En cas de divergence, rejouer ses commits sur le nouvel état plutôt que fusionner :
`git reset --hard origin/develop` puis `git cherry-pick`.

---

## 2 bis. Installer les hooks après chaque clone · *procédure*

```bash
make hooks          # ou : uv run pre-commit install
```

**Pourquoi ce n'est pas automatique.** `.pre-commit-config.yaml` n'est qu'une déclaration.
Git exécute `.git/hooks/pre-commit`, un fichier que `pre-commit install` crée — et
`.git/hooks` n'est jamais versionné. Un clone n'hérite donc d'aucun hook, et le fichier de
configuration reste inerte tant que personne n'a lancé la commande. `make install` s'en
charge désormais.

**Ce que les hooks exécutent.**

| Hook | Rôle |
|---|---|
| `ruff-check`, `ruff-format` | Linter et formatage, **avec la version du projet** |
| `catalogue-tests` | Régénère `docs/TESTS.md` dès qu'un test change |
| `gitleaks` | Empêche qu'un secret entre dans l'historique |
| contrôles de base | Fin de fichier, espaces, TOML, YAML, JSON, conflits, gros fichiers |

**Ruff passe par `uv run`, et non par un dépôt de hooks distant.** Un hook distant embarque
sa propre version : le fichier déclarait `v0.6.9` quand le verrou installe `0.16.9`. Deux
linters différents finissent par diverger — le hook reformate ce que la CI refuse, ou
l'inverse. Passer par `uv run` garantit une version unique, celle de `uv.lock`.

**Les hooks tournent aussi en CI.** Un développeur peut ne pas les avoir installés, ou les
contourner avec `--no-verify`. Surtout, `gitleaks` ne s'exécute nulle part ailleurs : sans
cette étape, le scanner de secrets serait décoratif.

## 3. Le notebook de certification ne se régénère pas · *partiellement vérifiée*

`notebooks/cas_usage_churn_saas.ipynb` le vérifie statiquement, sans attendre le pipeline.

| code | explications |
|---|---|
| `make test-doc` | Régénère `docs/TESTS.md` |
| `make test-doc-check` | Vérifie que le catalogue correspond aux tests livrés |
| `make format` | Reformate le code |
| `make hooks` | Installe les contrôles pre-commit dans `.git/hooks` |

Les carnets de phase — `01_cadrage`, `02_donnees`, etc. — sont des documents de travail
distincts. Ils établissent les faits et les décisions ; le notebook de certification en
reprend les conclusions, à la main, quand elles sont stabilisées.

**Motif.** Régénérer le livrable ferait perdre les ajustements manuels et les sorties déjà
validées. Le gel du notebook est un jalon de projet, pas une étape technique.

**Contrôle.** `test_le_notebook_de_certification_reste_sans_sorties` vérifie qu'il ne porte
aucune sortie avant le gel : des sorties versionnées feraient produire un diff à chaque
exécution, noyant les vraies modifications. Le reste de la règle — ne pas le reconstruire
par script — relève toujours de la discipline : c'est une décision de projet, pas un
contrôle technique.

---

## 4. Trois sorties par phase · *discipline*

| Sortie | Forme | Destinataire |
|---|---|---|
| Carnet de phase | `.ipynb` **exécuté**, sorties incluses | Le jury, et vous-même |
| Document d'explications | `.md` sans prérequis technique, avec glossaire | Un lecteur non spécialiste |
| Éléments de soutenance | Encadrés « À dire en soutenance » dans le `.md` | Vous, à l'oral |

Un carnet non exécuté ne prouve rien. Un document sans glossaire suppose des acquis que le
jury n'a pas nécessairement.

---

## 5. Tests de non-régression à chaque phase · *vérifiée*

Chaque phase ajoute ses tests **et** vérifie que les précédentes tiennent toujours.

`tests/test_non_regression_cadrage.py` fige les chiffres sur lesquels repose le cadrage :
volumétrie, taux de churn, concentration à 68 % et 72 %, facteur 100 entre seuils extrêmes,
hypothèses de coût. Ces valeurs sont citées dans trois livrables et dans la présentation
orale — un changement silencieux de la chaîne de nettoyage les invaliderait toutes à la
fois.

---

## 6. Séparation par activité du cycle de vie · *vérifiée*

Le code est organisé par activité, pas par type d'objet.

| # | Activité | Paquet |
|---|---|---|
| 1 | Gestion des données (bronze → silver → gold) | `donnees/` |
| 2 | Contrôle des features | `features/` |
| 3 | Modélisation (baseline et sélection) | `modelisation/` |
| 4 | Évaluation de la performance | `evaluation/` |
| 5 | Packaging (artefacts et fiche modèle) | `packaging/` |
| 6 | Services d'industrialisation | `industrialisation/` |
| 7 | Services de monitoring | `monitoring/` |

Quatre règles sont contrôlées par `tests/test_structure.py` : les sept activités existent et
rien d'autre ; chacune annonce son numéro et expose un `__all__` ; les dépendances suivent
l'ordre du cycle de vie ; les activités communiquent par leur interface publique, jamais par
un sous-module d'une autre.

Détail et graphe de dépendances : `docs/00.ORGANISATION_CODE.md`.

---

## 7. Une seule source de vérité pour le code · *vérifiée*

Le code vit dans `src/churn_saas/`, testé par `pytest`. Les carnets l'importent et
**affichent son source** au moment où ils l'expliquent, via `afficher_source()`.

Le code affiché est lu dans le module à l'instant de l'affichage : il ne peut donc pas
diverger de la version testée. `tests/test_notebook.py` garantit cet invariant.

**Ce que la règle interdit :** recopier une fonction dans un carnet. Deux versions
divergent toujours, et une seule est testée.

---

## 8. Mesurer plutôt que supposer · *discipline*

Toute affirmation du livrable s'appuie sur un calcul exécuté et visible.

| Affirmation | Ce qui la fonde |
|---|---|
| « L'absence d'une valeur n'est pas un signal » | Écart maximal de 4,5 points mesuré, pour un taux global de 28 % |
| « La normalisation de la clé est indispensable » | 0 % d'appariement sans elle, 100 % avec |
| « La fuite a été détectée, pas supposée » | Corrélation de −0,881 relevée par un contrôle générique |
| « Le classement est robuste à l'hypothèse de rétention » | Composition identique de la liste pour *u* de 15 % à 40 % |

**Le corollaire compte autant :** une analyse annoncée dans le texte doit exister dans les
sorties. Une promesse non tenue coûte plus cher qu'une promesse non faite.

---

## 9. Documenter les revirements · *discipline*

Un choix révisé est consigné avec son motif et sa date, jamais corrigé en silence.

| Décision | Position initiale | Motif du revirement |
|---|---|---|
| Git-LFS pour les CSV | Retenu | Un clone sans `git-lfs` récupère des pointeurs de 128 octets, sans erreur |
| Optuna | Écarté au nom de l'éco-conception | L'argument portait sur l'étendue de la recherche, pas sur l'outil |
| MLflow | Écarté, « surdimensionné » | La convention de nommage ne survit ni à plusieurs réentraînements ni à plusieurs opérateurs |
| Seuil de décision global | Retenu | Le seuil rationnel varie d'un facteur 130 selon la valeur du compte |

**Motif.** Le référentiel attend une démarche scientifique, laquelle se reconnaît aux
hypothèses invalidées autant qu'aux hypothèses confirmées. Le journal des itérations
(annexe D du livrable) récapitule ces retours.

---

## 10. Tester ce qui casse sans bruit · *discipline*

La suite ne vise pas la couverture de lignes. Elle vise les défauts qui ne lèvent aucune
erreur.

| Défaut silencieux | Test qui le couvre |
|---|---|
| Jointure perdant des lignes par différence de casse | `test_jointure_catalogue_sans_perte_malgre_la_casse` |
| Virgule décimale mal convertie | `test_nombres_stockes_en_texte` |
| Variable en fuite réintroduite par un remaniement | `test_gold_retire_les_colonnes_interdites` |
| Infini propagé par une division par zéro | `test_ratio_protege_contre_la_division_par_zero` |
| Tableau tronqué amputant un argument | `test_le_tableau_affiche_ne_tronque_aucune_cellule` |
| Manifeste réécrit sans raison, noyant les vrais changements | `test_le_manifeste_n_est_pas_reecrit_sans_raison` |

Un défaut bruyant se corrige en dix minutes. Un défaut silencieux se découvre en
soutenance.

Catalogue complet : `docs/TESTS.md`, généré par `make test-doc`.

---

## 11. Documents générés plutôt que rédigés · *vérifiée*

`docs/TESTS.md` est produit par `tools/catalogue_tests.py` à partir des fichiers de tests.
Un inventaire écrit à la main dérive dès le premier test ajouté, et un inventaire périmé
revendique une couverture qui n'existe plus.

La CI vérifie que le catalogue livré correspond aux tests livrés.

**Corollaire :** un document qui contredit l'outil qu'il prétend décrire coûte plus cher
qu'un document absent.

---

## 12. Signaler ses propres erreurs · *discipline*

Une erreur introduite est signalée, avec sa cause, plutôt que corrigée discrètement.

Exemples consignés : un `rm` avec accolades qui n'a rien supprimé sous `/bin/sh` et a laissé
sept modules fantômes ; un manifeste reconstruit à chaque exécution, produisant un diff à
chaque commit ; un catalogue annonçant 64 cas quand pytest en collectait 75.

**Motif.** Chacune de ces erreurs aurait fini par se manifester à un moment plus coûteux.
Et une erreur cachée dans un dépôt de certification est une question du jury à laquelle on
n'a pas de réponse.

---

## Commandes utiles

```bash
make install-plateforme   # environnement complet
make check                # tous les contrôles, dans l'ordre où la CI les exécute
make executer-notebook    # rejoue le notebook de certification de bout en bout
```

**`make check` reproduit exactement la CI** : tests, linter, fraîcheur du catalogue, format.
Le lancer avant de pousser transforme un échec de pipeline découvert après coup en un
message d'une ligne découvert avant.

| Cible | Contrôle |
|---|---|
| `make test` | Suite de tests |
| `make lint` | Style du code, carnets compris |
| `make test-doc` | Régénère `docs/TESTS.md` |
| `make test-doc-check` | Vérifie que le catalogue correspond aux tests livrés |
| `make format` | Reformate le code |

**Périmètre du linter sur les carnets.** Un carnet est un livrable narratif, pas du code de
production : longueur de ligne, ordre des imports, instructions sur une même ligne et
imports volontairement commentés y sont tolérés, et la liste est justifiée ligne par ligne
dans `pyproject.toml`. Ce qui reste actif est ce qui casse — `F821`, nom indéfini, a déjà
détecté un `RandomForestRegressor` utilisé sans import qui aurait interrompu l'exécution du
livrable.
