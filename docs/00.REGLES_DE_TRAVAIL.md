# Règles de travail du projet

> Ce document consigne les conventions appliquées à chaque contribution. Il existe pour
> deux raisons : qu'un nouvel arrivant n'ait pas à les deviner, et qu'aucune ne repose sur
> la seule mémoire de ceux qui les ont posées.
>
> Les règles marquées **vérifiée** sont contrôlées par la suite de tests. Les autres
> relèvent de la discipline, et sont donc les plus fragiles.

---

## 1. Langue du code · *vérifiée*

**Commentaires et docstrings en anglais**, dans tout le code source et dans les cellules de
code des carnets.

**Contenu affiché en français** : cellules markdown, titres et libellés de figures, noms de
colonnes des tableaux produits, messages imprimés et messages d'exception.

| Élément | Langue | Motif |
|---|---|---|
| Commentaires `#` | Anglais | Convention usuelle, lisible par tout relecteur technique |
| Docstrings | Anglais | Elles documentent l'implémentation, pas le livrable |
| Noms de fonctions et de variables | Français | Héritage assumé ; renommer l'API publique est une opération à mener hors période de remise |
| Markdown des carnets | Français | Le livrable est lu par un jury francophone |
| Titres et libellés de figures | Français | Idem |
| Messages imprimés et d'exception | Français | Ils apparaissent dans les sorties remises |

Le résultat est un hybride assumé : identifiants français, commentaires anglais. C'est un
compromis fréquent en contexte professionnel francophone.

**Contrôle :** `tests/test_conventions.py` signale tout commentaire ou docstring contenant
un caractère accentué — un indice fiable et peu coûteux de prose française. Le même fichier
vérifie l'inverse sur les tables affichées : leur contenu doit rester accentué.

## 2. Synchronisation avant toute mise à jour · *procédure*

Avant de commencer quoi que ce soit :

```bash
git fetch origin
git log --oneline -3 origin/develop
git rev-list --left-right --count origin/develop...HEAD
```

**Pourquoi.** L'historique distant a déjà été réécrit une fois. Travailler sur une base
périmée produit des patchs qui ne s'appliquent plus et, pire, des corrections qui écrasent
celles de quelqu'un d'autre.

En cas de divergence, rejouer ses commits sur le nouvel état plutôt que fusionner :
`git reset --hard origin/develop` puis `git cherry-pick`.

## 2 bis. Installer les hooks après chaque clone · *procédure*

```bash
make hooks          # ou : uv run pre-commit install
```

**Pourquoi ce n'est pas automatique.** `.pre-commit-config.yaml` n'est qu'une déclaration.
Git exécute `.git/hooks/pre-commit`, un fichier que `pre-commit install` crée — et
`.git/hooks` n'est jamais versionné. Un clone n'hérite donc d'aucun hook, et le fichier de
configuration reste inerte tant que personne n'a lancé la commande. `make install` s'en
charge désormais.

**Ce que les hooks exécutent.**

| Hook | Rôle |
|---|---|
| `ruff-check`, `ruff-format` | Linter et formatage, **avec la version du projet** |
| `catalogue-tests` | Régénère `docs/TESTS.md` dès qu'un test change |
| `gitleaks` | Empêche qu'un secret entre dans l'historique |
| contrôles de base | Fin de fichier, espaces, TOML, YAML, JSON, conflits, gros fichiers |

**Racine temporaire des tests.** `tests/conftest.py` vérifie au démarrage que la racine
temporaire est exploitable, et bascule sinon sur `~/.pytest-temp` avec un avertissement
nommant la cause. Sans ce garde-fou, un dossier `pytest-of-<utilisateur>` devenu illisible
faisait échouer d'un coup les treize tests utilisant `tmp_path`, pour une raison étrangère
au code.

**Ne jamais utiliser `--basetemp` pointant dans le dépôt** : pytest **efface** ce répertoire
au démarrage, et Windows refuse dès qu'un processus y tient une poignée ouverte.

**Ruff passe par `uv run`, et non par un dépôt de hooks distant.** Un hook distant embarque
sa propre version : le fichier déclarait `v0.6.9` quand le verrou installe `0.16.9`. Deux
linters différents finissent par diverger — le hook reformate ce que la CI refuse, ou
l'inverse. Passer par `uv run` garantit une version unique, celle de `uv.lock`.

**Les hooks tournent aussi en CI.** Un développeur peut ne pas les avoir installés, ou les
contourner avec `--no-verify`. Surtout, `gitleaks` ne s'exécute nulle part ailleurs : sans
cette étape, le scanner de secrets serait décoratif.

## 3. Le notebook de certification ne se régénère pas · *partiellement vérifiée*

`notebooks/cas_usage_churn_saas.ipynb` le vérifie statiquement, sans attendre le pipeline.

| code | explications |
|---|---|
| `make test-doc` | Régénère `docs/TESTS.md` |
| `make test-doc-check` | Vérifie que le catalogue correspond aux tests livrés |
| `make format` | Reformate le code |
| `make hooks` | Installe les contrôles pre-commit dans `.git/hooks` |

Les carnets de phase — `01_cadrage`, `02_donnees`, `03_exploration` — sont des documents
de travail distincts. Ils établissent les faits et les décisions ; le notebook de
certification en reprend les conclusions, à la main, quand elles sont stabilisées. À partir
de la phase 4, il n'y a plus de carnet de phase : les sections 7 à 13 sont rédigées
directement dans le notebook de certification (règle 4 amendée). L'interdiction de le
reconstruire par script reste entière.

**Motif.** Régénérer le livrable ferait perdre les ajustements manuels et les sorties déjà
validées. Le gel du notebook est un jalon de projet, pas une étape technique.

**Révision du 03/10/2026 — le notebook est versionné avec ses sorties** (choix B du porteur).
Jusque-là, il restait sans sorties jusqu'au gel. Désormais, le dépôt montre les résultats sans
qu'il faille exécuter le notebook ; le coût accepté est un diff de sorties à chaque exécution.
Il s'exécute en entier, en place, par `make executer-notebook`.

**Contrôle.** `test_le_notebook_de_certification_est_execute_en_entier_sans_erreur` vérifie que
des sorties versionnées sont **dignes de confiance** : soit aucune, soit **une seule exécution
complète**, du début à la fin (compteurs 1, 2, …, n), sans cellule en erreur ni chemin du poste.
Des cellules relancées à la main afficheraient des résultats que le code, exécuté dans l'ordre,
ne produit pas. Le reste de la règle — ne pas le reconstruire par script — relève toujours de la
discipline : c'est une décision de projet, pas un contrôle technique.

## 4. Trois sorties par phase · *discipline* · amendée le 01/10/2026

Un carnet non exécuté ne prouve rien. Un document sans glossaire suppose des acquis que le
jury n'a pas nécessairement. Ces deux principes valent pour toutes les phases ; c'est la
forme des sorties qui change à partir de la phase 4.

### Phases 1 à 3 · forme d'origine

| Sortie | Forme | Destinataire |
|---|---|---|
| Carnet de phase | `.ipynb` **exécuté**, sorties incluses | Le jury, et vous-même |
| Document d'explications | `.md` sans prérequis technique, avec glossaire | Un lecteur non spécialiste |
| Éléments de soutenance | Encadrés « À dire en soutenance » dans le `.md` | Vous, à l'oral |

Les carnets `01_cadrage`, `02_donnees` et `03_exploration` et leurs documents
d'explications restent en l'état : ils ne sont ni supprimés ni réécrits.

### Phases 4 à 11 · forme amendée

| Sortie | Forme | Destinataire |
|---|---|---|
| Preuve exécutée | Sections 7 à 13 du notebook de certification, rédigées directement et **exécutées au gel** (règle 3) | Le jury |
| Éléments de soutenance | Encadrés « À dire en soutenance », regroupés dans `docs/04.SOUTENANCE_phases_4_a_11.md` | Vous, à l'oral |
| Glossaire | Termes nouveaux uniquement, dans ce même fichier ; les termes déjà définis aux phases 1 à 3 ne sont pas répétés | Un lecteur non spécialiste |

**Ce qui disparaît** pour ces phases : le carnet de phase séparé (`04_…`, `05_…`) et le
document d'explications vulgarisé complet.

**Révision du 02/10/2026 — carnet de travail rétabli à partir de la phase 5.** À la demande du porteur,
chaque phase peut de nouveau avoir son **carnet de travail exécuté** (`05_feature_engineering.ipynb`), qui
montre la démarche avec ses figures et ses tableaux. Le notebook de certification reste **la preuve remise** :
les conclusions y sont reportées, avec le même code, importé de `src/` (règle 7). Le document d'explications
vulgarisé complet reste supprimé : encadrés et glossaire vont dans `04.SOUTENANCE_phases_4_a_11.md`.
Motif : relire une phase dans un carnet qui lui est dédié est plus simple que de la chercher dans un notebook
de plus de 70 cellules ; le coût du double report est accepté, car le code n'est pas dupliqué.

**Ce qui ne disparaît pas** : l'exigence de preuve exécutée et l'exigence de glossaire.
Les encadrés sont conservés parce qu'ils alimentent directement la banque de réponses
préparée pour l'oral.

**Motif du revirement.** La remise est fixée au lundi 05/10/2026 au matin. Les phases 1 à
3 ont occupé les journées du 29/09 au 01/10 (historique Git) ; il reste quatre jours pour
les phases 4 à 11. Dans la forme d'origine, chaque conclusion est écrite deux fois : dans
le carnet de phase, puis reportée à la main dans le notebook de certification (règle 3).
Rédiger directement dans le livrable supprime ce report sans supprimer la preuve.

**Risque introduit et parade.** Avant le gel, le notebook de certification ne porte aucune
sortie versionnée (règle 3) : un chiffre écrit dans son texte n'est donc adossé à aucun
calcul visible dans le dépôt. Chaque chiffre cité dans les sections 7 à 13 est figé par un
test de non-régression au moment où il est écrit (règle 5), et non au gel. Un chiffre sans
test n'est pas cité.

## 5. Tests de non-régression à chaque phase · *vérifiée*

Chaque phase ajoute ses tests **et** vérifie que les précédentes tiennent toujours.

`tests/test_non_regression.py` fige les chiffres sur lesquels repose le cadrage :
volumétrie, taux de churn, concentration à 68 % et 72 %, facteur 100 entre seuils extrêmes,
hypothèses de coût. Ces valeurs sont citées dans trois livrables et dans la présentation
orale — un changement silencieux de la chaîne de nettoyage les invaliderait toutes à la
fois.

## 6. Séparation par activité du cycle de vie · *vérifiée*

Le code est organisé par activité, pas par type d'objet.

| # | Activité | Paquet |
|---|---|---|
| 1 | Gestion des données (bronze → silver → gold) | `donnees/` |
| 2 | Contrôle des features | `features/` |
| 3 | Modélisation (baseline et sélection) | `modelisation/` |
| 4 | Évaluation de la performance | `evaluation/` |
| 5 | Packaging (artefacts et fiche modèle) | `packaging/` |
| 6 | Services d'industrialisation | `industrialisation/` |
| 7 | Services de monitoring | `monitoring/` |

Quatre règles sont contrôlées par `tests/test_structure.py` : les sept activités existent et
rien d'autre ; chacune annonce son numéro et expose un `__all__` ; les dépendances suivent
l'ordre du cycle de vie ; les activités communiquent par leur interface publique, jamais par
un sous-module d'une autre.

Détail et graphe de dépendances : `docs/00.ORGANISATION_CODE.md`.

## 7. Une seule source de vérité pour le code · *vérifiée*

Le code vit dans `src/churn_saas/`, testé par `pytest`. Les carnets l'importent et
**affichent son source** au moment où ils l'expliquent, via `afficher_source()`.

Le code affiché est lu dans le module à l'instant de l'affichage : il ne peut donc pas
diverger de la version testée. `tests/test_notebook.py` garantit cet invariant.

**Ce que la règle interdit :** recopier une fonction dans un carnet. Deux versions
divergent toujours, et une seule est testée.

## 8. Mesurer plutôt que supposer · *discipline*

Toute affirmation du livrable s'appuie sur un calcul exécuté et visible.

| Affirmation | Ce qui la fonde |
|---|---|
| « L'absence d'une valeur n'est pas un signal, sur les colonnes reçues » | Écart maximal de 4,5 points mesuré, pour un taux global de 28 % — la phase 3 a montré que la conclusion ne vaut pas pour les colonnes construites, où l'écart atteint 62 points |
| « La normalisation de la clé est indispensable » | 54,3 % d'appariement sans elle, 100 % avec : 2 302 lignes perdues en silence |
| « La fuite a été détectée, pas supposée » | Corrélation de −0,881 relevée par un contrôle générique |
| « Le classement est robuste à l'hypothèse de rétention » | Composition identique de la liste pour *u* de 15 % à 40 % |

**Le corollaire compte autant :** une analyse annoncée dans le texte doit exister dans les
sorties. Une promesse non tenue coûte plus cher qu'une promesse non faite.

## 10. Tester ce qui casse sans bruit · *discipline*

La suite ne vise pas la couverture de lignes. Elle vise les défauts qui ne lèvent aucune
erreur.

| Défaut silencieux | Test qui le couvre |

| Jointure perdant des lignes par différence de casse | `test_jointure_catalogue_sans_perte_malgre_la_casse` |
| Virgule décimale mal convertie | `test_nombres_stockes_en_texte` |
| Variable en fuite réintroduite par un remaniement | `test_gold_retire_les_colonnes_interdites` |

soutenance.

Catalogue complet : `docs/TESTS.md`, généré par `make test-doc`.

## 11. Documents générés plutôt que rédigés · *vérifiée*

`docs/TESTS.md` est produit par `tools/catalogue_tests.py` à partir des fichiers de tests.
Un inventaire écrit à la main dérive dès le premier test ajouté, et un inventaire périmé
revendique une couverture qui n'existe plus.

La CI vérifie que le catalogue livré correspond aux tests livrés.

**Corollaire :** un document qui contredit l'outil qu'il prétend décrire coûte plus cher
qu'un document absent.

**Une mesure prise sur le poste est une entrée, pas un texte.** Les ressources du poste de
développement et les temps de calcul mesurés vivent dans `config/ressources_poste.toml` ;
`docs/06.SOBRIETE_calcul.md` en est généré. Seul le rendu est vérifié en CI : y refaire la mesure
décrirait la machine de la CI, pas le poste.

**Quand un document ne peut pas être généré, il est vérifié.** L'arborescence du `README.md`
porte une description par fichier, qu'aucun générateur ne saurait écrire : elle reste rédigée,
mais quatre tests de `tests/test_structure.py` la confrontent au paquet. Un module ajouté sans
sa ligne, ou une ligne laissée par un module supprimé ou renommé, fait échouer la suite — donc
la CI. À sa mise en place, le contrôle a trouvé `features/graphiques.py` absent du README.

## 12. Signaler ses propres erreurs · *discipline*

Une erreur introduite est signalée, avec sa cause, plutôt que corrigée discrètement.

Exemples consignés : un argument présenté comme une mesure (« dates ambiguës : 1,2 mois d'écart à
l'ancienneté en lisant le jour en premier, 3,0 en lisant le mois ») calculé sur des dates ISO elles-mêmes
mal lues — la conclusion était juste pour les dates à barres obliques, la mesure ne l'établissait pas, et
elle masquait le défaut sur les dates ISO ; un `rm` avec accolades qui n'a rien supprimé sous `/bin/sh` et a laissé
sept modules fantômes ; un manifeste reconstruit à chaque exécution, produisant un diff à
chaque commit ; un catalogue annonçant 64 cas quand pytest en collectait 75.

**Motif.** Chacune de ces erreurs aurait fini par se manifester à un moment plus coûteux.
Et une erreur cachée dans un dépôt de certification est une question du jury à laquelle on
n'a pas de réponse.

## 13. Tracer ce qui est laissé de côté · *vérifiée*

Ce qui est écarté, différé ou en attente d'arbitrage est consigné dans **un registre unique**,
avec son motif, sa preuve et, s'il n'est pas définitif, la condition à laquelle on y revient.

| Élément | Rôle |
|---|---|
| `docs/registre_ecarts.toml` | **Source**, éditée à la main : une entrée par élément |
| `MOTIFS_EXCLUSION` (code) | Colonnes exclues du modèle, lues par le générateur et jamais recopiées (règle 7) |
| `docs/05.REGISTRE_elements_ecartes.md` | **Généré** par `make registre-doc`, jamais édité (règle 11) |

Trois statuts, qui ne se confondent pas : **écarté** (décision définitive), **différé** (faute
de temps), **à arbitrer** (décision attendue du porteur). Un élément différé ou à arbitrer
sans condition de réexamen est un abandon qui ne dit pas son nom.

**Motif.** Le règlement attend les éléments volontairement exclus (section 2), les
alternatives écartées (section 7) et les limites (section 13). Dispersés dans six documents,
ils ne répondaient pas à la question que le jury posera : *qu'avez-vous laissé de côté,
pourquoi, et à quelle condition y reviendriez-vous ?*

**Contrôle.** `tests/test_registre.py` vérifie les champs obligatoires, l'unicité des
identifiants, la condition de réexamen, l'existence des preuves citées, la fraîcheur du
document, et qu'**aucune colonne ne disparaît du modèle sans motif** — contrôle générique,
qui ne nomme aucune colonne. La CI et `make check` vérifient que le document est à jour.

## 14. Tester par campagne · *vérifiée*

À chaque activité, deux niveaux de tests, déclarés dans `tests/campagnes.toml` :

| Niveau | Contenu | Commande |
|---|---|---|
| **Tests courants** | Les tests des modules **créés ou modifiés** pendant l'activité, marqués `@pytest.mark.<activité>` | `make test-courants` |
| **Non-régression** | Les fichiers qui prouvent que l'activité s'intègre : chiffres publiés et garanties des phases précédentes, structure, conventions, documents générés | `make test-non-regression` |
| Les deux | — | `make test-activite` (aussi lancé au pre-push) |
| Toute la suite | — | `make test` ; **l'intégration continue lance toujours toute la suite** |

**Motif.** Relancer les quelque 500 tests à chaque modification ralentit le travail sans rien apprendre de plus
sur l'activité en cours. La campagne cible ce qui vient de changer et ce qui pourrait en souffrir ; la CI reste
le filet complet.

**Changer d'activité.** Ajouter une section `[campagnes.<activité>]`, déclarer son marqueur dans
`pyproject.toml` (marqueurs stricts : une faute de frappe échoue au lieu de ne rien sélectionner), marquer les
tests des modules touchés, puis mettre à jour `activite`. Les tests des activités précédentes **gardent leur
marqueur** et restent dans le filet : la campagne les relance au niveau non-régression
(`marqueurs_precedents`). Un test **modifié** pendant l'activité **change de marqueur** : il prend celui de
l'activité en cours. Un test ne porte jamais deux marqueurs d'activité — il tournerait deux fois.

**Contrôle.** `tests/test_campagnes.py` vérifie que l'activité courante a sa campagne, que chaque marqueur est
déclaré, que chaque fichier de non-régression existe, qu'aucun test ne tourne deux fois, et que le niveau
« courants » sélectionne bien des tests — une campagne vide passerait sans rien tester.

## Commandes utiles

```bash
make install-plateforme   # environnement complet
make check                # tous les contrôles, dans l'ordre où la CI les exécute
make executer-notebook    # rejoue le notebook de certification de bout en bout
```

**`make check` reproduit exactement la CI** : tests, linter, fraîcheur du catalogue et du
registre, format.
Le lancer avant de pousser transforme un échec de pipeline découvert après coup en un
message d'une ligne découvert avant.

**Les tests y sont exécutés dans un environnement construit comme celui de la CI**, avec
le seul groupe `dev`. L'environnement local contient tous les groupes : une dépendance
héritée par transitivité y fonctionne et échoue dans le pipeline. C'est ainsi que
`nbformat` est passé — importé par les tests, fourni par `nbconvert` dans le groupe
`notebook`, absent de la CI.

**Règle qui en découle :** une dépendance utilisée par les tests se déclare dans le
groupe `dev`, jamais héritée d'un autre groupe. `test_les_dependances_des_tests_sont_declarees`
le vérifie statiquement, sans attendre le pipeline.

| Cible | Contrôle |
|---|---|
| `make test` | Suite de tests, environnement local |
| `make test-ci` | Suite de tests dans un environnement identique à la CI |
| `make lint` | Style du code, carnets compris |
| `make test-doc` | Régénère `docs/TESTS.md` |
| `make test-doc-check` | Vérifie que le catalogue correspond aux tests livrés |
| `make format` | Reformate le code |
| `make registre-doc` | Régénère le registre des éléments écartés (règle 13) |
| `make registre-doc-check` | Vérifie que le registre correspond à sa source |
| `make test-activite` | Campagne de l'activité : tests courants puis non-régression (règle 14) |
| `make test-courants` · `make test-non-regression` | Chacun des deux niveaux séparément |
| `make materialiser` | Réécrit silver, gold et découpage au manifeste, sans Jupyter |
| `make hooks` | Installe les contrôles pre-commit dans `.git/hooks` |

**Périmètre du linter sur les carnets.** Un carnet est un livrable narratif, pas du code de
production : longueur de ligne, ordre des imports, instructions sur une même ligne et
imports volontairement commentés y sont tolérés, et la liste est justifiée ligne par ligne
dans `pyproject.toml`. Ce qui reste actif est ce qui casse — `F821`, nom indéfini, a déjà
détecté un `RandomForestRegressor` utilisé sans import qui aurait interrompu l'exécution du
livrable.
