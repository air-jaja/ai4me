# Ingestion et gouvernance des données — explications accessibles

> Document d'accompagnement du carnet `notebooks/02_donnees.ipynb`.
> **Écrit pour être compris sans connaissance technique.** Chaque section explique d'abord
> de quoi il s'agit, puis ce qui a été constaté et décidé.
>
> Les encadrés **« À dire en soutenance »** proposent une formulation courte, réutilisable
> telle quelle à l'oral.

---

## De quoi parle cette phase

La phase précédente a défini le problème à résoudre. Celle-ci s'occupe de la matière
première : **les données**.

Quatre questions, qui paraissent administratives et ne le sont pas du tout :

1. Que contiennent réellement les fichiers qu'on nous a donnés ?
2. Comment ces données vivent-elles dans le temps — d'où viennent-elles, combien de temps
   les garde-t-on, quand les supprime-t-on ?
3. Où les ranger, et pourquoi là plutôt qu'ailleurs ?
4. Qu'y a-t-il de confidentiel là-dedans, et qu'en fait-on ?

Un projet peut être techniquement excellent et échouer sur ces quatre points. C'est même
fréquent : on se concentre sur le modèle, et l'on découvre six mois plus tard qu'on ne sait
plus sur quelles données il a appris, ni si l'on avait le droit de les utiliser.

---

## 1. Que contiennent vraiment les données ?

### Le principe : lire d'abord, comprendre ensuite

Les fichiers sont lus **intégralement comme du texte**, sans laisser le programme deviner
la nature de chaque colonne.

Cela peut sembler un détour inutile. C'en est un si les données sont propres. Ici, elles ne
le sont pas — et volontairement : l'énoncé de l'exercice précise que des défauts ont été
introduits, et qu'il fait partie du travail de les trouver.

Si l'on laisse le programme deviner, il fait des choix silencieux. Une colonne contenant
`33,3` sera comprise comme du texte et non comme un nombre. Le programme ne dira rien. Et
plus tard, un calcul donnera un résultat absurde sans qu'on sache pourquoi.

### Ce que veut dire « le rôle » d'une colonne

Le type d'une colonne dit comment elle est écrite. Son **rôle** dit ce qu'on a le droit
d'en faire. Les deux sont très différents.

| Rôle | Exemple | Ce qu'on peut en faire |
|---|---|---|
| Identifiant | Le numéro du client | Rien — il ne prédit rien, il désigne |
| Cible | Le client est-il parti ? | C'est ce qu'on cherche à prédire |
| Usage | Nombre de connexions | Servir de signal au programme |
| Postérieur à la décision | Score calculé après coup | **Rien** — l'information n'existait pas encore |
| Texte libre | Notes du conseiller | Rien — risque de données personnelles |

Sur 29 colonnes, **six ne peuvent pas servir au programme**, et pour six raisons
différentes. Cette distinction compte : dire « on les enlève parce qu'elles dégradent le
résultat » serait faux pour la plupart d'entre elles.

### Les défauts trouvés, et ce qu'ils coûtent

Quatre défauts ont été mesurés, pas supposés.

| Défaut constaté | Ce qui se passerait si on ne le corrigeait pas |
|---|---|
| 35 lignes en double sur 5 035 | Le programme apprend deux fois les mêmes exemples et sa note est flattée |
| Un caractère invisible en tête de fichier | La première colonne devient introuvable par son nom |
| Des nombres écrits comme du texte | Chaque valeur devient une catégorie : « 33,3 » et « 33,4 » n'ont plus aucun rapport |
| Des majuscules incohérentes sur une clé | Le rapprochement entre fichiers échoue **sans message d'erreur** |

**Le dernier est de loin le plus dangereux**, et c'est contre-intuitif.

Les trois premiers provoquent une erreur franche : le programme s'arrête, on cherche, on
corrige. Le quatrième ne provoque rien du tout. Le nom d'une formule d'abonnement s'écrit
`STARTER` dans un fichier et `Starter` dans l'autre ; l'ordinateur les considère comme deux
choses différentes ; les lignes concernées disparaissent silencieusement du résultat.

Nous avons mesuré l'effet : **sans harmonisation préalable, 2 302 lignes sur 5 035 — près
d'une sur deux — ne seraient pas rapprochées**. Avec harmonisation, toutes le sont.

Le chiffre mérite une seconde de réflexion. Un échec total se remarquerait : un tableau
vide, une colonne entièrement absente. Un échec à 46 % ne se remarque pas. Les données
restent plausibles, les moyennes restent crédibles, et l'analyse porte sur la moitié du
portefeuille sans que rien ne l'indique.

> **À dire en soutenance.** « Le défaut le plus coûteux n'est pas celui qui provoque une
> erreur, c'est celui qui n'en provoque aucune. Une majuscule mal placée sur une clé de
> rapprochement fait disparaître des lignes sans rien signaler. Nous avons mesuré l'écart
> plutôt que de supposer que la correction était utile. »

### Une question que nous avons testée plutôt que tranchée

Entre 3 et 10 % des valeurs manquent, selon les colonnes. La réaction habituelle consiste à
les remplacer par une estimation — la valeur moyenne des autres clients, par exemple.

Mais une autre hypothèse est possible : et si **l'absence d'une donnée était elle-même un
signal** ? Un client désengagé pourrait cesser d'être suivi, et le vide dans ses données
indiquerait son désintérêt bien avant son départ.

Nous avons vérifié. Pour chaque colonne, nous avons comparé le taux de départ des clients
dont la donnée est présente à celui des clients dont elle est absente. **L'écart maximal est
de 4,5 points**, pour un taux moyen de 28 %. C'est trop faible pour conclure.

L'hypothèse est donc écartée — sur la base d'une mesure, pas d'une intuition. Et c'est cette
vérification qui justifie la méthode de remplacement retenue à l'étape suivante.

> **À dire en soutenance.** « Nous avons testé l'hypothèse qu'un trou dans les données
> puisse être un signal. L'écart mesuré est de 4,5 points, trop faible pour conclure. Nous
> l'écartons sur la base d'une mesure, et c'est ce qui légitime la méthode de remplacement
> que nous retenons ensuite. »

## 2. Le cycle de vie des données

Une donnée n'est pas un objet figé qu'on range une fois pour toutes. Elle naît, circule,
est utilisée, conservée, puis supprimée. Huit étapes ont été décrites, chacune avec sa
fréquence, sa durée et **son responsable nommé**.

| Étape | En clair |
|---|---|
| Collecte | On récupère les données depuis les systèmes de l'entreprise |
| Ingestion | On les lit telles quelles et on vérifie qu'elles ressemblent à ce qu'on attend |
| Préparation | On les nettoie et on les met en forme |
| Instantané | On fige une photographie datée, qui servira de référence |
| Exploitation | On calcule les scores et on les transmet aux équipes |
| Conservation | On garde l'historique des scores |
| Archivage | On garde les photographies pour pouvoir revenir en arrière |
| Purge | On supprime ce qui a dépassé la durée prévue |

**Pourquoi nommer un responsable pour chaque étape ?** Parce qu'une étape sans responsable
est une étape que personne n'exécute. La purge en est l'exemple type : tout le monde
approuve le principe, personne ne la fait, et l'entreprise conserve des données sans base
légale pendant des années.

**Un point est laissé volontairement ouvert** : la durée de conservation des scores. Deux
exigences s'opposent. Surveiller le bon fonctionnement du programme demande de garder un
historique long. Le respect de la réglementation demande de ne pas garder plus que
nécessaire. Cet arbitrage appartient au délégué à la protection des données et à la
direction, pas à l'équipe technique.

> **À dire en soutenance.** « Nous avons attribué un responsable à chacune des huit étapes.
> Une seule question reste ouverte, la durée de conservation des scores : elle oppose le
> suivi du modèle à la minimisation des données, et cet arbitrage ne nous appartient pas. »

## 3. Où ranger les données, et pourquoi

### Le problème

Les fichiers doivent être rangés quelque part, et le choix n'est pas neutre. On veut
pouvoir revenir à la version d'il y a trois mois, savoir qui a modifié quoi, et permettre à
quelqu'un d'autre de reproduire nos résultats.

### Six solutions possibles

| Solution | Principe, en une phrase |
|---|---|
| **Git** | L'outil qui garde l'historique du code ; il peut aussi garder des fichiers |
| **Git-LFS** | Une extension pour les gros fichiers : Git garde un ticket, le fichier va ailleurs |
| **DVC** | Un outil spécialisé qui relie une version de données à une version de code |
| **Stockage objet** | Un espace en ligne où l'on dépose des fichiers qu'on ne modifie jamais |
| **Base de données** | Un magasin interrogeable, où l'on cherche par critères |
| **Entrepôt analytique** | Une base de très grande capacité, pour des volumes énormes |

### Ce que nous avons appris par l'expérience

Le dépôt du projet avait d'abord été configuré avec **Git-LFS**. Nous avons récupéré une
copie depuis un environnement où l'extension n'était pas installée. Résultat :

**Les trois fichiers étaient là, mais ils pesaient 128 octets au lieu de 700 000.** Ils ne
contenaient pas les données, seulement un ticket. Aucun message d'erreur.

C'est exactement le même piège que la clé de rapprochement mal harmonisée : une défaillance
qui ne dit pas son nom. Un correcteur qui récupérerait le projet sans l'extension se
retrouverait avec trois fichiers illisibles et un programme qui échoue plus loin, sur un
message sans rapport avec la vraie cause.

### La décision

| Type de donnée | Où | Pourquoi |
|---|---|---|
| Les fichiers de départ (2 Mo) | **Git simple** | En dessous de 50 Mo, Git suffit et n'exige rien de particulier |
| Les photographies d'entraînement | **Stockage objet** | Fichiers qu'on ne modifie jamais, conservés hors du dépôt |
| Les scores produits | **Base de données** | On a besoin de les interroger, pas de les versionner |
| Les fiches de version | **Git simple** | Minuscules, lisibles, et ce sont elles le contrat |

**Git-LFS n'est pas mauvais** — il devient le bon choix au-delà de quelques dizaines de
mégaoctets. À 2 Mo, il ajoute une contrainte sans contrepartie.

> **À dire en soutenance.** « Nous avions choisi Git-LFS. Un test nous a montré qu'un clone
> sans l'extension récupère des fichiers de 128 octets, sans erreur. Nous sommes revenus à
> Git simple : à deux mégaoctets, LFS ajoute une dépendance et un risque d'échec silencieux
> sans rien apporter. Nous documentons ce revirement plutôt que de le corriger en silence. »

### Versionner les données, pas seulement le programme

Garder l'historique du programme est facile. Garder celui des données est l'endroit où tout
se perd.

Imaginons : un modèle a été entraîné il y a trois mois. On veut refaire exactement le même
calcul. On récupère le programme dans sa version d'alors. Mais les données, elles, ont été
mises à jour entre-temps — et **rien ne le signale**.

La solution s'appelle une **empreinte**. C'est un code calculé à partir du contenu d'un
fichier, une sorte de signature. Si le contenu change d'un seul caractère, l'empreinte
change entièrement. Elle répond donc à une question précise : *est-ce bien le même jeu de
données qu'à l'époque ?*

Nous avons produit une **fiche de version** qui enregistre l'empreinte de chaque fichier
source. Avant chaque entraînement, on la vérifie. Si une empreinte ne correspond plus,
c'est que quelque chose a changé, et l'on en est averti avant de produire un résultat qui
ne reproduit rien.

> **À dire en soutenance.** « Nous versionnons trois choses ensemble : le programme, les
> données et le modèle. Chaque fichier source porte une empreinte enregistrée dans une
> fiche de version. Avant tout entraînement, on vérifie qu'elle correspond toujours. Sans
> cela, la reproductibilité est une affirmation, pas une propriété. »

## 4. Ce qu'il y a de confidentiel

### Trois niveaux à distinguer

« Sensible » ne veut pas dire uniquement « données personnelles ».

| Niveau | Exemple ici | Pourquoi c'est sensible |
|---|---|---|
| **Donnée personnelle** | Notes libres du conseiller | Peuvent nommer des personnes, porter des jugements |
| **Pseudonyme** | Numéro du client | Permet de remonter à une entreprise identifiable |
| **Confidentiel commercial** | Revenu d'un client | Information stratégique, même sans personne physique |

**Une confusion très répandue** : un numéro de client n'est pas une donnée anonyme. Il
suffit d'une autre table pour retrouver l'entreprise. La réglementation appelle cela un
**pseudonyme**, et le traite comme une donnée personnelle.

### Mesurer plutôt que supposer

Le champ de notes libres est rempli dans 45 % des comptes. Dire qu'il *pourrait* contenir
des données personnelles est confortable et invérifiable.

Nous l'avons donc analysé automatiquement, en cherchant des adresses électroniques, des
numéros de téléphone, des noms de personnes et des liens internet. Le résultat figure dans
le carnet.

**Les exemples affichés sont masqués avant d'apparaître.** Montrer du texte libre brut dans
un document remis à un jury constituerait en soi une divulgation. La démonstration ne doit
pas commettre la faute qu'elle décrit — et le masquage est fait par le programme, donc
systématique.

**Décision :** ce champ est exclu, pour un motif réglementaire et non statistique. S'il
s'avérait très prédictif, cela ne changerait rien.

### Le piège des variables indirectes

Certaines colonnes ne sont pas confidentielles mais peuvent servir de **substitut** à une
caractéristique protégée. Le pays, le secteur d'activité, la taille de l'entreprise en font
partie.

Nous avons mesuré les écarts de taux de départ entre leurs différentes valeurs. Ils restent
modérés, et aucune catégorie n'est trop peu représentée pour être fiable.

**Nous les conservons donc**, et c'est un choix délibéré qui mérite explication.

La réaction instinctive serait de les supprimer par précaution. Ce serait une fausse bonne
idée : le programme reconstituerait l'information à partir d'autres colonnes qui y sont
liées, **et plus aucun indicateur ne permettrait de le détecter**. En les gardant et en les
surveillant, on conserve la capacité de mesurer.

> **À dire en soutenance.** « Nous avons gardé les variables qui pourraient servir de
> substitut à une caractéristique protégée, au lieu de les supprimer. Les retirer aurait
> donné une illusion d'équité : le modèle aurait reconstitué l'information autrement, sans
> qu'on puisse le voir. Les garder et les surveiller est plus honnête et plus efficace. »

## 5. Ce que cette phase a décidé

| Décision | En une phrase |
|---|---|
| Tout lire en texte d'abord | Ne pas laisser l'ordinateur faire des choix silencieux |
| Harmoniser les clés avant rapprochement | Éviter la perte de lignes sans message d'erreur |
| Ne pas traiter les trous comme un signal | Hypothèse testée, écart mesuré trop faible |
| Git simple plutôt que Git-LFS | À 2 Mo, LFS ajoute un risque sans bénéfice |
| Photographies d'entraînement hors du dépôt | Fichiers figés, adressés par empreinte |
| Scores en base de données | On les interroge, on ne les versionne pas |
| Fiche de version avec empreintes | Seul moyen de savoir si les données ont changé |
| Notes libres exclues | Motif réglementaire, pas statistique |
| Variables indirectes gardées et surveillées | Les retirer donnerait une illusion d'équité |

### Ce qui reste à trancher, et par qui

| Question | Qui décide |
|---|---|
| Combien de temps conserver les scores | Délégué à la protection des données et direction |
| Mise en place effective du stockage en ligne | Équipe infrastructure |
| Fréquence réelle des extractions | Équipe données et systèmes sources |

## Glossaire

| Terme | Définition |
|---|---|
| **Clé de rapprochement** | Colonne commune à deux fichiers, permettant de les relier |
| **Cycle de vie** | Parcours d'une donnée, de sa collecte à sa suppression |
| **DPO** | Délégué à la protection des données, garant du respect du RGPD |
| **Empreinte (hash)** | Signature calculée à partir du contenu d'un fichier ; change entièrement si le contenu change |
| **Git** | Outil conservant l'historique des modifications d'un projet |
| **Git-LFS** | Extension de Git pour les fichiers volumineux ; nécessite une installation côté utilisateur |
| **Gouvernance** | Ensemble des règles définissant qui fait quoi avec les données, et pendant combien de temps |
| **Imputation** | Remplacement d'une valeur manquante par une estimation |
| **Ingestion** | Lecture des données depuis leur source, sans transformation |
| **Instantané (snapshot)** | Photographie datée d'un jeu de données, figée pour référence |
| **Jointure** | Opération reliant deux fichiers par une colonne commune |
| **Manifeste** | Fiche recensant les fichiers d'une version et leurs empreintes |
| **Parquet** | Format de fichier compact adapté aux gros volumes de données tabulaires |
| **Pseudonyme** | Identifiant permettant de remonter à une personne ou entreprise via une autre source |
| **Purge** | Suppression définitive des données au terme de leur durée de conservation |
| **RGPD** | Règlement européen sur la protection des données personnelles |
| **Schéma** | Description des colonnes d'un jeu de données : nom, type, rôle |
| **Stockage objet** | Espace de stockage en ligne pour fichiers immuables (Amazon S3, MinIO…) |
| **Variable indirecte (proxy)** | Colonne qui approche une caractéristique protégée sans la nommer |
| **Versionnement** | Conservation de l'historique des états successifs d'un élément |
